# 云端后台部署

当前版本使用 WebSocket/WSS 全程服务器转发。玩家从比赛平台或其他渠道拿到完整游戏包，云端只运行账号、房间、实时对战转发和排行榜，不分发游戏资源。房主浏览器计算比赛，服务器负责按房间和角色校验并转发。双方不需要互相访问，不使用 WebRTC、STUN/TURN 或玩家之间的 UDP。

仓库提供可部署版本，尚未实际部署公网地址。公网服务必须从玩家网络可达；公司对外访问策略仍可能限制连接。旧的内网 IP 不会因为改为转发模式而变成公网地址。

## 准备服务器

1. 准备有公网 IPv4 的 Linux 服务器，并安装 Docker Engine 和 Docker Compose 插件。初期十人测试可从 2 核、2 GB 起步，容量以实测为准。
2. 准备自己管理的域名，例如 `game.example.com`，添加 A 记录指向服务器公网 IPv4。不要添加指向不可用地址的 AAAA 记录。
3. 在云安全组和主机防火墙放行 TCP 80、443。SSH 管理端口只放行管理员来源。后台的 8766 端口不需要向公网开放。
4. 中国大陆部署按接入商要求办理备案；购买/领取前核对试用资格、实例抵扣、流量额度和到期费用。

Docker 官方安装文档：https://docs.docker.com/engine/install/ubuntu/

## 上传并启动

上传并解压 `dist/BadmintonAce-Cloud.zip` 到服务器目录，例如 `/opt/badminton-ace`。这是纯后台包，不含模型、WASM、PCK、Windows EXE 或玩家数据库。也可以使用完整仓库；Docker 构建仅复制后台所需文件。

在解压目录执行：

```sh
cp deploy/.env.example deploy/cloud.env
```

编辑 `deploy/cloud.env`，把示例改成实际域名，只写域名，不带 `https://`：

```dotenv
GAME_DOMAIN=game.example.com
```

随后执行：

```sh
docker compose --env-file deploy/cloud.env up -d --build
docker compose --env-file deploy/cloud.env ps
docker compose --env-file deploy/cloud.env logs --tail=80 server https
```

Compose 启动 Node.js 后台和 Caddy。域名解析正确、80/443 可达后，Caddy 自动申请并续期 HTTPS 证书。后台进程随容器重启，数据库保存在 `game_data` 持久卷；证书也使用持久卷。不要运行 `docker compose down -v`，它会删除卷里的数据。

通过玩家网络打开 `https://game.example.com/health`，应看到 `ok: true`、`version: 5`、`transport: "websocket-relay"` 和 `lanOnly: false`。根路径只显示后台服务信息，访问 `/index.html`、`/index.wasm`、`/index.pck` 返回 404，云端不提供游戏下载。

## 配置玩家游戏包

把游戏包 `config.js` 中的赋值改为实际云端地址：

```js
window.ACE_SERVER = 'wss://game.example.com/ws';
```

如果从完整仓库发布，修改 `tools/web-config.js` 后重新导出；只分发已有网页包时，可直接修改 `build/web/config.js`。必须让 HTTPS 比赛平台和本地文件两种打开方式都使用这个 WSS 地址，不要保留仅在 `file:` 时才生效的条件赋值。

将完整网页包提交比赛平台或发给玩家。玩家照常打开 `index.html`，登录 → 在线对战 → 创建或浏览房间。公开房可直接加入，密码房要求密码。不需要分享服务器根网址作为游戏下载链接；后台模式不生成指向自身 `/index.html` 的无效邀请。

如果比赛平台嵌入网页且限制外连，需要允许连接 `wss://game.example.com`。HTTPS 页面不能使用不安全的 `ws://` 地址。

## 数据、管理和更新

云端使用单实例后台和 SQLite，房间保存在该进程内存中；不要直接复制多个后台实例并轮询分流。扩容多实例需要另外设计共享房间状态。服务更新会中断当前对局，安排在无人对战时执行。

备份时先停后台，再复制数据库目录，最后恢复：

```sh
docker compose --env-file deploy/cloud.env stop server
docker compose --env-file deploy/cloud.env cp server:/app/data ./backup-data
docker compose --env-file deploy/cloud.env start server
```

使用新的空备份目录，完整保存 SQLite 数据及其配套文件；备份包含账号数据和管理密钥，不要公开或提交 Git。云端 Caddy 明确拒绝 `/gm`，后台 GM 仍只接受本机请求。容器部署的管理请求应在后台容器内通过 `127.0.0.1:8766` 发出，并使用 `/app/data/gm-key.txt` 验证；不要为了管理而把 GM 接口开放到公网。

上传新版后台文件后，在该目录重新运行 `docker compose --env-file deploy/cloud.env up -d --build`。保留同一目录、`deploy/cloud.env` 和数据卷。更新玩家游戏包与后台协议时，两边一起更新。

## 流量与检查

云端只计算联机通信流量，游戏资源由其他渠道提供。服务器出站流量包括转发给双方的状态、操作、账号及房间消息。人数、实际对战时长、消息频率和传输开销都会影响账单；实例试用额度与公网流量额度需分别核对。

上线前用两个真实网络的电脑检查登录、公开/密码房、开赛、双向移动击球、暂停、断线判负及排行榜。仓库自动测试会禁用 WebRTC 并验证两浏览器仍可通过服务器完成对打，但不代替真实公网连通性、延迟和容量压测。
